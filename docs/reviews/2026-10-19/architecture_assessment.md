## 值得保留的设计

| 设计 | 价值与边界 |
| --- | --- |
| btcore 与 adapters/factors/strategies 分层 | 用户扩展不需要改内核；反破坏检查约束依赖方向 |
| T 信号、T+1 撮合；裸价/hfq 分工 | 将金融正确性约束放在明确执行阶段，便于独立核算 |
| YAML 因子 + DAG + 固定算子表 | 依赖列、warmup 和公共子表达式可推导，避免恢复因子类层次与注册框架 |

| stats 纯函数、数据库显式事务 | 统计可脱离存储验证；事务不承诺恢复任意策略或外部副作用 |
| ledger_fills/meta 为事实源 | 可按新策略重放同一成交史；当前全量回放和衍生表重写有明确成本 |
| 模型 meta、artifact 哈希、导出一致性校验 | 已有模型字节完整性保护；无需从零重建模型版本机制 |

## 按收益排序的改进

### 1. 先修每日生命周期分叉（P1，ARCH-LIVE-01）

位置：`research.live.replay_ledger`；对照 `Engine.step/compute_pending`。

`compute_pending` 同时负责持仓计日、解锁、无行情时清空订单，以及有行情时执行策略钩子。
回测每日调用它；实盘回放只在 `bars_dict` 非空时调用。这使一个“是否决策”的判断，
意外控制了“交易日状态是否推进”。

探针通过真实 `run_signal` 入口使用内存账本：20240603/04/05 为三个交易日，04 日无行情。
期初持仓 100 股，策略持有满 3 天卖出。期末实际计数 2、卖单为空，独立期望为 3、有卖单。
这是支持路径的操作单错误，不以低频降级。

建议先做最小修复：在需要回放决策状态的路径中，无行情日也执行已实现的空行情处理，
由引擎保证不调用决策钩子；加三日完整入口回归，再验证正常行情和公司行为往返一致。
后续若继续调整结构，将“推进交易日状态”与“执行策略决策”分开，两个入口共享前者。
不要为修复此问题立即重写整个引擎。

F-ENG-02 修复的是回测入口，此次是实盘独立入口的新证据，不重开已正确修复的代码。
实际资金影响、所有 holding 模型的受影响范围未验证。

### 2. 补全运行身份（P3，ARCH-RUN-01）

位置：`Engine.run`、`strategy_loader.build_strategy`、`database.SCHEMA_SQL`。

策略装配将 factor_specs、filter_rules、因子闭包放在实例属性上；结果库主要存
`strategy.config` 和两项资金/仓位覆盖值。探针将因子权重由 1 改为 2，生效权重不同，
两次 `config_json` 却完全一致。仅凭结果库无法还原这项配置区别。

建议增加带版本的运行清单，保存规范化后的完整策略声明、因子闭包及其摘要、策略源码
与内核版本、数据源快照标识、模型 ONNX 和 meta 身份、关键依赖版本。代码 commit
无法覆盖被忽略的本地策略，因此还需记录实际内容身份。数据文件路径/mtime 只能作
弱身份提示；最好使用数据生产方提供的快照版本，避免每次全量散列大型行情库。

模型已有 artifact_sha256，不应声称模型“完全无版本管理”。新增清单也不能凭空恢复
旧结果缺失的配置；旧 run 应明确标注追溯信息不完整。

### 3. 统一数据准备的配置解析与编排

位置：`Engine.prepare`、`ml.dataset.build_panel`、`scripts.ml_train.main`。

当前共享了因子规划、派生、伪列和物化函数，但准备顺序、基准选择、计算域与告警处理
仍由多个调用方独立编排。共享底层函数不等于整个准备流程只有一个事实源。
静态可见：引擎对物化告警 level 有白名单，训练端直接 getattr；引擎推导默认基准，
训练 CLI 直接读取 config.benchmark。历史 F-ML-04、F-FD4-07 已登记相关差异，
本轮不重复登记或宣称已重新动态验证。

建议先提取纯粹的 resolved 配置/数据请求计划，再复用查询与物化服务；训练和回测
分别保留标签构建、账户状态、时点锚定。训练不应 import Engine，也不应强行复用
完整 prepare（它还会 attach provider、启动策略等）。验收比较同一数据版本和计算域
下的面板值、NaN 掩码、列序，以及未来扰动后的历史前缀。

### 4. 收紧跨模块的数据结构，减少隐式接线

位置：`engine._validate_select_actions`、`strategy_loader._attach_universe`、
`backend.DataBackend`、`generic_sql.GenericSQLBackend.__init__`。

select 七键协议、配置与因子计划大量使用 dict；loader 会给策略实例挂属性和替换
universe hook，后端也按表单动态挂能力方法。它们提供灵活性，但阅读类定义不能得到
完整运行行为，接口变动主要依赖运行期校验和测试发现。

建议先为稳定边界增加 TypedDict/小型数据类和可选能力 Protocol，保留 YAML/dict
用户接口与现有 fail-fast 校验。只有触及相关功能时再显式化装配结果；不为类型标注
另造插件框架，不恢复被禁止的 Factor/StrategyAdapter 类层次。这是演进方案，
不是本轮新增已复现计算缺陷，也不需要现在全仓改签名。

### 5. 在保持等价性的前提下优化广度与回放（P3，ARCH-PERF-01）

位置：`factors.library.compute_breadth`、`research.live.run_signal`。

广度查询分块，但每块都将新数据拼接到完整历史，再计算整个前缀。12 行、块大小 4
的探针实际输入量为 4+8+12=24，结果仍正确。固定块大小 b、共 k 块时，物化输入量
为 b*k*(k+1)/2（未计 warmup）。这是工作量推导，不是实测耗时复杂度或加速比。

当前前缀保留有充分理由：停牌样本和 pandas 滚动累加浮点差异可能翻转边界判断。
建议先按读取/派生/物化/推理/撮合/写库记录耗时及峰值内存；有数据版本和计划摘要后，
优先考虑物化缓存。增量算子必须证明停牌、复牌、EMA、NaN 和阈值比较的一致性，
不直接截断历史或降精度。

signal 的全量回放同样有长期成本，但 checkpoint 必须包含账户、pending、条件单及
策略状态，并绑定数据/策略/模型版本。当前没有通用策略状态快照契约，不能只存账户
就宣称可以等价续跑。因此 checkpoint 应晚于运行身份与状态契约，且需全量回放对照。
